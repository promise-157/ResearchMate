# M15 本地资料搜索评估

## 结论

当前阶段不迁移 SQLite FTS，也不引入 embedding。现有精确子串 `LIKE` 搜索在 50,000 条合成真实规模资料上最慢的中位数约 22 ms；这尚未构成本地个人工作区的用户瓶颈。FTS5 trigram 对三字以上选择性查询更快，但会让评估数据库体积增加约 164%，且一至两个汉字仍必须回退到 `LIKE`。

该结论不是永久拒绝 FTS。出现以下任一事实时重新运行评估：典型工作区超过 50,000 条资料、搜索 API 的服务端 p95 超过 100 ms、用户需要相关度排序/高亮，或接受层以外出现第二种需要统一索引的文本来源。

## 方法

评估脚本为 `src/scripts/evaluate_material_search.py`。它只在临时目录创建工作区形状的 SQLite 数据库，不读取用户工作区、`src/data/`、配置、Key 或网络。

数据包含 10,000 和 50,000 条中英文标题/正文、四种资料类型、三种状态以及独立的已接受 OCR。九类查询覆盖：

- 高频与选择性中文；
- 英文大小写；
- 字面 `%` 和 `_`；
- 默认排除及显式包含已接受 OCR；
- 类型/状态组合过滤；
- 一至两个汉字的 trigram 回退。

每类查询预热后执行 15 次，并比较完整结果 ID，所有 LIKE 与 FTS 原型结果集合一致。性能数字是本机架构判断依据，不作为 CI 门槛。

## 结果摘要

| 规模 | 原数据库 | 含 FTS | FTS 增幅 | 建索引 |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 5.40 MiB | 14.18 MiB | 162.5% | 96 ms |
| 50,000 | 26.33 MiB | 69.47 MiB | 163.8% | 579 ms |

50,000 条时的中位数：

| 查询 | LIKE | FTS/回退 |
| --- | ---: | ---: |
| 高频两字中文 | 21.8 ms | 21.4 ms（LIKE 回退） |
| 选择性中文 | 10.7 ms | 0.5 ms |
| 选择性英文 | 7.7 ms | 1.2 ms |
| 显式搜索已接受 OCR | 14.7 ms | 0.2 ms |
| 类型与状态组合 | 7.3 ms | 0.6 ms |
| 一至两个汉字 | 10.5–10.6 ms | 10.4–10.5 ms（LIKE 回退） |

## 迁移成本

真正采用 FTS 需要幂等 schema 迁移、现有工作区回填，以及对资料创建/更新/删除和 OCR 接受/重新接受的事务内同步；归档导入还要校验或可靠重建派生索引。当前延迟收益不足以证明这些复杂度合理。

Embedding 解决的是语义相似而非精确查找，不能替换现有子串契约。只有脱敏真实查询集证明用户经常“不知道原词但知道意思”时，才评估可选本地 embedding。
